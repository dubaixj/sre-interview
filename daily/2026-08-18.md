## 第 1 题：部分用户打不开，另一部分人正常

### 题目

用户访问 `www.example.com`：一部分人浏览器转圈超时，一部分人正常。  
你在自己电脑上：

- `dig A www.example.com` 得到 `10.0.0.10`
- `curl http://10.0.0.10` 和服务器上 `curl http://127.0.0.1` 都是 200

值班同事说「服务器没问题」。

1. 为什么「服务器 200」还不能结案？
2. 下一步必须先查什么？写出命令。
3. 如果 A 记录对，但 AAAA 指向一个不通的 IPv6，会出现什么现象？怎么证实？
4. 如何证明这是 DNS 问题，而不是 Nginx / 安全组问题？

### 标准答案

「本机 / 服务器 200」只能证明：**这台机器上的 Nginx、本机回环、以及你当前解析到的这个 IPv4 是通的**。  
它证明不了：所有用户解析到同一个地址、IPv6 是否可达、CDN/旧缓存/错误 CNAME 是否把一部分人带到别的 IP。

用户访问的是**域名**，不是 IP。部分人失败、部分人成功，第一优先查 **DNS 结果是否一致**，不要先改 Nginx，也不要先改安全组。

```bash
# 权威对照：A 和 AAAA 都要查，不要只查 A
dig A www.example.com
dig AAAA www.example.com
dig CNAME www.example.com
dig NS example.com
dig A www.example.com @8.8.8.8
dig A www.example.com @114.114.114.114
dig AAAA www.example.com @8.8.8.8

# 看本机实际拿到什么（含 IPv6）
getent ahosts www.example.com
# 或
getent ahostsv4 www.example.com
getent ahostsv6 www.example.com

# 绕过 DNS，强制走 IPv4 / IPv6
curl -4 -v --connect-timeout 5 http://www.example.com/
curl -6 -v --connect-timeout 5 http://www.example.com/
curl --resolve www.example.com:80:10.0.0.10 -v --connect-timeout 5 http://www.example.com/
```

AAAA 指向不通的 IPv6 时，常见现象：

- 双栈客户端（很多手机 / 新系统浏览器）优先走 IPv6，连不上就转圈，等到 IPv6 超时才回退 IPv4，表现为「一部分人慢或超时」；
- 只做 IPv4 的客户端（或 `curl` 默认 A）完全正常；
- 所以你会看到「我这边 200、用户那边不行」。

证实：

```bash
dig AAAA www.example.com +short          # 看有没有 AAAA、是不是死地址
curl -6 -v --connect-timeout 5 http://www.example.com/
# 服务器上确认自己根本没听 IPv6 或没这条地址
ip -6 addr
ss -tlnp | grep ':80'
```

证明是 DNS 而不是 Nginx / 安全组：

| 观察 | 结论 |
|---|---|
| `curl --resolve ...:10.0.0.10` 200 | 这台 IPv4 上的 Nginx 正常 |
| `curl -4` 200、`curl -6` 超时 | 问题在 AAAA / IPv6 路径，不是 80 没监听 |
| 不同 DNS 服务器给出不同 A | 缓存、权威记录、CDN 调度不一致 |
| 服务器 `tcpdump` 抓不到失败用户的 SYN | 用户根本没打到这台机器（解析错了或卡在入口） |
| 安全组漏放通常是**所有外网**超时，不是「一部分人」 | 不要先改安全组 |

处理：修权威 DNS（删掉错误 AAAA，或补上真实可达的 IPv6）；等 TTL；让失败用户 `dig` 对照。改完用 `dig A/AAAA` + `curl -4/-6` 两边都通再结案。

### 面试可背模板

> 部分人失败、部分人成功，先当 DNS 结果不一致，不要先动 Nginx。A 和 AAAA 都要 `dig`，再用 `curl -4` / `curl -6` / `--resolve` 对照。AAAA 指到死地址时，双栈客户端会先走 IPv6 超时。本机 200 只证明当前这条 IPv4，证明不了所有用户解析都对。

### 详细口述模板（按面试官小问答）

**开口：**  
同事说服务器 200，只能说明**他这条路径**通。用户访问的是域名，部分失败首先怀疑解析结果不一样，尤其是只查了 A、没查 AAAA。

**1. 为什么服务器 200 不能结案**  
它只证明：这台机器 Nginx 在、`10.0.0.10:80` 通、回环通。排除不了：用户解析到旧 IP / CDN / 错误 AAAA、本地 DNS 缓存、只 IPv6 失败。

**2. 下一步必须先查 DNS**

```bash
dig A www.example.com
dig AAAA www.example.com
dig A www.example.com @8.8.8.8
curl -4 -v --connect-timeout 5 http://www.example.com/
curl -6 -v --connect-timeout 5 http://www.example.com/
curl --resolve www.example.com:80:10.0.0.10 -v http://www.example.com/
```

**3. A 对、AAAA 是死地址**  
双栈客户端优先 IPv6，连不上就转圈超时；纯 IPv4 客户端正常。`curl -6` 能复现，`curl -4` 不能。

**4. 怎么证明是 DNS 不是 Nginx / 安全组**  
`--resolve` 到 `10.0.0.10` 是 200，说明 Nginx 没问题。失败用户的包如果 `tcpdump` 都没有，人没打到这台机器。安全组漏放一般是全员外网超时，不是一部分人。

**30 秒压缩版：**  
部分人打不开先 `dig A` 和 `dig AAAA`，再用 `curl -4/-6` 对照。本机 200 不等于所有人解析都对；AAAA 死地址专坑双栈客户端。

### 现场记录

- 作答：部分人失败不是整站/Nginx/防火墙，先当 DNS；自己这边 A + IPv4 curl 200 只说明 IPv4 通，AAAA 还没查，怀疑一部分用户走到坏的 IPv6。追问：先 `dig AAAA`，有地址再本机 `curl -6`，再到服务器上 `curl -6` 对照；远端超时、本机 IPv6 通则偏安全组，服务器本机也不通则偏服务。再追问：`ip -6 addr` 和解析出的 AAAA 比对；不是这台机器则这台 `tcpdump` 看不到失败用户的包。
- 评分：主答 7 / 10；追问 7 / 10；再追问 9 / 10
- 扣分点：命令没写全（要 `dig AAAA` / `curl -4` / `curl -6` / `ip -6 addr`）；「不是 Nginx/防火墙」说太死；「AAAA 解析不出来 = DNS 坏了」不成立（很多站本来就没有 AAAA，经典坑是有 AAAA 但死地址）；服务器上不要 `curl -6 127.0.0.1`；第一轮追问漏了「AAAA 是不是这台机器」
- 再追问：`ip -6 a` 对照 AAAA；不是这台则 tcpdump 看不到。口径对。

## 第 2 题：502、503、504 分别卡在哪

### 题目

同一套 `客户端 → Nginx → Spring Boot:8080`。三次故障用户侧状态码不同，error.log 分别是：

```text
A. connect() failed (111: Connection refused) while connecting to upstream
B. no live upstreams while connecting to upstream
   （或 Nginx 直接 return 503；limit_req 拒绝）
C. upstream timed out (110: Connection timed out) while reading response header from upstream
```

1. A/B/C 通常分别对应 502 / 503 / 504 的哪一种？各说明哪一段坏了？
2. 三种情况下一步命令有什么不同？
3. 出现 C 时，为什么不能先重启 Nginx？
4. 把 `proxy_read_timeout` 调大，算不算把根因修了？

### 标准答案

| 现象 | 常见状态码 | 含义 | 优先查 |
|---|---|---|---|
| A Connection refused | **502** | Nginx 作为网关，没从上游拿到有效响应；这里是连不上（没人听 / 地址端口错 / REJECT） | 后端进程、`ss -tlnp ':8080'`、直连 curl |
| B no live upstreams / 限流 / 主动 503 | **503** | 网关认为当前**没有可用后端**，或主动拒绝服务（过载保护） | upstream 探活是否全挂、限流、容量 |
| C read header timed out | **504** | 已经把请求交给上游，但在超时时间内没返回响应头 | 后端慢查询 / 依赖卡住 / 超时是否过短 |

502 ≠ 后端代码一定写错；503 ≠ 一定是应用 503；504 ≠ Nginx 挂了。

```bash
# 共同：先分类，再动手
tail -n 100 /var/log/nginx/error.log
curl -vI http://127.0.0.1/api/user
nginx -T | grep -A30 'upstream\|location /api\|proxy_read_timeout\|max_fails'

# A 502 refused：先看有没有人听
ss -tlnp | grep ':8080'
systemctl status myapp --no-pager
journalctl -u myapp -n 100 --no-pager
curl -v --connect-timeout 5 http://127.0.0.1:8080/api/user

# B 503：看探活和限流，不要先重启 Nginx
# upstream 里 server ... max_fails=N fail_timeout=Ns;
# 直连每个后端，看是真挂了还是探活误杀
curl -v http://10.0.0.11:8080/actuator/health
curl -v http://10.0.0.12:8080/actuator/health

# C 504：直连后端看是慢还是死
curl -v --max-time 60 http://127.0.0.1:8080/api/user
ss -antp | grep ':8080'
journalctl -u myapp -n 200 --no-pager
# 再查后端依赖：DB / Redis / 下游 HTTP，而不是先动 Nginx
```

C 时不能先重启 Nginx 的原因：504 说明 **反向代理自己往往是好的**，它在等上游。重启 Nginx 会丢掉当前连接、可能短时间雪崩，但慢查询 / 锁等待 / 下游超时还在。先看 error.log 里的 `timed out`，再直连后端计时。

把 `proxy_read_timeout` 调大：只是让网关多等一会儿。若根因是 SQL 打满、线程池耗尽、下游挂了，调大只会让更多请求堆在 Nginx 和 JVM 里，**不是根因修复**。先定位慢在哪，超时只作为保护值，改完要压测对比。

### 面试可背模板

> 502 是没拿到上游有效响应，refused 就先看端口。503 是网关认为没活后端或主动限流。504 是上游太慢没在超时内回来，先直连后端计时，不要先重启 Nginx。调大 timeout 只是多等，不是根因。

### 详细口述模板（按面试官小问答）

**开口：**  
三个码都是网关侧的话，但卡的位置不同。先读 error.log 分类，再决定查监听、探活还是后端耗时。

**1. 对照**  
A → 502，连不上上游。  
B → 503，没有活的上游或主动拒绝。  
C → 504，上游接了但响应头没在超时里回来。

**2. 命令不同**  
502 refused：`ss -tlnp`、进程、直连 8080。  
503：查 upstream 探活、`max_fails`、限流，逐台直连 health。  
504：`curl --max-time` 直连看耗时，再查 DB/下游，不先动 Nginx。

**3. 为什么 504 不先重启 Nginx**  
Nginx 多半只是在等。重启会丢连接，根因还在应用或依赖。

**4. 调大 timeout 算不算修好**  
不算。那是保护值。根因是慢查询或依赖，调大只会堆更多请求。

**30 秒压缩版：**  
error.log 分类：refused 查监听，no live 查探活，timed out 查后端慢。504 别先重启 Nginx，也别只靠调大 timeout。

## 第 3 题：删了 20G 日志，`df` 还是 100%

### 题目

`/var/log` 所在分区 `df -h` 显示 100%。你删掉了已经轮转出来的 `access.log.1`（约 20G），立刻再跑 `df -h` 还是 100%。Nginx 仍在跑。`df -i` 显示 inode 只用了 15%。

1. 空间为什么可能没回来？
2. 用哪些命令确认？每条证明什么？
3. 怎么安全释放？能不能 `rm` 正在写的 `access.log`？
4. 这题和「inode 满」、「根分区够但日志盘满」分别怎么区分？

### 标准答案

最常见原因：**文件目录项删了，但进程还握着这个 fd**，内核要等最后一个 fd 关闭才真正释放块。Nginx worker 如果还开着旧的 `access.log.1`（或你误删了正在写的 `access.log`），`df` 就不会掉。

次常见：删错挂载点、删的是软链另一头不在这个分区、快照/预留空间、短时间内又写满。

本题 inode 只有 15%，**不是 inode 耗尽**。

```bash
df -h /var/log
df -i /var/log                 # 排除 inode
lsof +L1                       # link count=0 但仍打开的文件
# 或
lsof | grep -i deleted
lsof -nP /var/log/nginx/
# 看具体 fd
ls -l /proc/$(pgrep -n -f 'nginx: worker')/fd | grep deleted

du -xh -d 1 /var/log | sort -h
# du 偏小、df 仍满：典型「已删未释放」
```

安全释放：

```bash
# 1) 确认是谁占着：一般是 nginx worker
# 2) 让 Nginx 重新打开日志，而不是 kill -9
nginx -t
nginx -s reopen          # 或 kill -USR1 <master_pid>
# systemd 托管也可用：
# systemctl reload nginx   # reload 会复用 reopen 语义，但先确认配置没问题

# 3) 若必须立刻回收且不能重启：对那个 fd 截断（慎用，先确认 inode/fd）
# : > /proc/<pid>/fd/<fd>

df -h /var/log           # 空间应下降
lsof +L1 | grep nginx    # deleted 项应消失
```

不要：

- `rm` 正在写的 `access.log` 再指望空间马上回来——不 reopen 一样占着；
- 默认 `kill -9` Nginx 抢空间——丢连接、systemd 可能拉起后问题还在；
- 当 inode 满去扫小文件，或当根分区问题去扩 `/`。

区分：

| 现象 | 判断 |
|---|---|
| `df -i` 100%，`df -h` 还有空 | inode 满（第 2 轮第 1 题） |
| `df -h /` 有空，`df -h /var/log` 100% | 独立分区，要对路径做 df |
| `df -h` 100%，`du` 对不上，`lsof +L1` 有 deleted | 已删未释放（本题） |

### 面试可背模板

> `rm` 只删目录项。进程还握着 fd，块不会还。`lsof +L1` 确认后，对 Nginx 用 `nginx -s reopen`，不要 `kill -9`，也不要盲删正在写的日志。`df -i` 能排除 inode；`du` 和 `df` 对不上就是这类问题。

### 详细口述模板（按面试官小问答）

**开口：**  
inode 只有 15%，这题不是 inode。删了 20G 立刻 `df` 不变，优先怀疑文件被删但 Nginx 还开着。

**1. 空间为什么没回来**  
内核按「还有没有进程打开」释放块，不是按目录里看不看得见。`rm` 完目录项没了，`du` 变小，`df` 仍满。

**2. 命令**

```bash
df -h /var/log
df -i /var/log
lsof +L1
lsof | grep deleted
du -xh -d 1 /var/log | sort -h
```

`df -i` 排除 inode；`lsof +L1` 抓已删仍打开；`du` 明显小于 `df` 就对上了。

**3. 安全释放**  
`nginx -t` 之后 `nginx -s reopen`（USR1），让 worker 关掉旧 fd、打开新日志。不要 `kill -9`，不要直接 `rm` 当前正在写的 `access.log` 当常规手段。释放后再 `df -h` 和 `lsof +L1`。

**4. 和另外两题的区别**  
inode 满看 `df -i`。分区看错是 `df -h /` 和 `df -h /var/log` 不一致。本题是 `du`/`df` 对不上 + `deleted`。

**30 秒压缩版：**  
删大文件 `df` 不变，先 `lsof +L1`。Nginx 占着就 `reopen`，别 `kill -9`。`df -i` 排除 inode。

## 第 4 题：巡检脚本在 Ubuntu 的 cron 里挂了

### 题目

你写了磁盘巡检脚本 `check_disk.sh`，自己在终端里 `bash check_disk.sh` 正常。放到 Ubuntu 24.04 的 crontab 后失败。脚本头是 `#!/bin/sh`，里面用了 `[[ ]]` 和未加引号的变量。cron 邮件里有：

```text
[[: not found
```

有一次改完后又出现 `unbound variable`（或变量是空的，`df` 打到了错误路径）。

1. 为什么交互式终端能跑、cron 挂？`sh`、`bash`、`dash` 分别是什么？
2. `#!/bin/bash` 和 `#!/usr/bin/env bash` 有什么差别？什么时候用哪个？
3. 生产脚本为什么要 `set -euo pipefail`？每一项防什么？
4. 写一个「磁盘使用率超过阈值就非 0 退出」的最小骨架（含 shebang 和严格模式）。

### 标准答案

Ubuntu 上 `/bin/sh` **软链到 dash**，不是 bash。dash 是 POSIX 精简壳，**不支持 `[[ ]]`、数组、bash 正则**。  
你在终端执行 `bash check_disk.sh` 是**指定了 bash**，绕过 shebang；cron 按 shebang 跑 `sh` → dash，于是 `[[: not found`。

| 解释器 | 是什么 | 关键限制 |
|---|---|---|
| bash | 完整 Bash | 运维脚本标准；支持 `[[ ]]` |
| dash | Debian/Ubuntu 的 POSIX sh | 快、精简，无 `[[ ]]` |
| `sh` | 在本机上是个软链 | Ubuntu 24.04 上就是 dash |

`chmod +x && ./script` 走 shebang；`bash script` 忽略 shebang。

```text
#!/bin/bash              内核去固定路径找 bash；集群路径统一时稳
#!/usr/bin/env bash      按 PATH 找 bash；跨发行版 / 容器更稳
```

课件口径：固定 Ubuntu/CentOS 集群两种都行，跨发行版用 `env`。巡检脚本只要用了 `[[ ]]`，shebang **必须是 bash**，不能是 `sh`。

`set -euo pipefail`：

| 选项 | 作用 | 防什么 |
|---|---|---|
| `-e` | 任一命令非 0 就退出 | 前面 `cd`/`mkdir` 失败了后面还继续删 |
| `-u` | 读未定义变量就退出 | 阈值、路径是空的，`rm -rf $DIR/` 变成灾难 |
| `-o pipefail` | 管道任一段失败则整段失败 | `cmd | awk` 里 cmd 挂了，awk 仍返回 0，报表是脏数据 |

`unbound variable` 就是 `-u` 在起作用：cron 的环境几乎是空的，`PATH`、你在 `.bashrc` 里的变量都没有。脚本必须自己写绝对路径、自己定义阈值。

最小骨架：

```bash
#!/usr/bin/env bash
set -euo pipefail

THRESHOLD="${1:-80}"
MOUNT="${2:-/}"

used=$(df -P "$MOUNT" | awk 'NR==2 {gsub(/%/, "", $5); print $5}')
if [[ -z "${used}" || ! "${used}" =~ ^[0-9]+$ ]]; then
    echo "failed to read disk usage for ${MOUNT}" >&2
    exit 2
fi

if (( used >= THRESHOLD )); then
    echo "ALERT ${MOUNT} used=${used}% threshold=${THRESHOLD}%" >&2
    exit 1
fi

echo "OK ${MOUNT} used=${used}%"
exit 0
```

crontab 注意：写绝对路径；用 `bash /opt/scripts/check_disk.sh 80 /`；不要依赖 `.bashrc`。退出码非 0 才能被监控/cron 当成失败。

### 面试可背模板

> Ubuntu 上 `sh` 是 dash，不认 `[[ ]]`。终端里 `bash script` 能跑，cron 按 shebang 走 `sh` 就会挂。巡检脚本 shebang 写成 bash，生产加 `set -euo pipefail`：`-e` 防继续跑，`-u` 防空变量，`pipefail` 防管道假成功。cron 环境是空的，路径和阈值都写死。

### 详细口述模板（按面试官小问答）

**开口：**  
这不是磁盘命令写错，是**解释器不是同一个**。终端用了 bash，cron 用了 `#!/bin/sh` → dash。

**1. 为什么终端能跑、cron 挂**  
`bash check_disk.sh` 强制 bash，忽略 shebang。cron 按第一行 `#!/bin/sh` 跑，Ubuntu 上 sh→dash，`[[` 当外部命令找，报 `[[: not found`。

**2. 两种 shebang**  
`#!/bin/bash` 写死路径；`#!/usr/bin/env bash` 按 PATH 找，跨系统更稳。用了 `[[ ]]` 就不能写 `sh`。

**3. set -euo pipefail**  
`-e` 失败即停；`-u` 未定义变量即停（防空路径）；`pipefail` 管道中段失败也算失败（防脏报表）。

**4. 骨架要点**  
bash shebang + 严格模式 + `df -P` 取使用率 + `[[ ]]` 校验数字 + 超阈值 `exit 1`。cron 里写绝对路径。

**30 秒压缩版：**  
Ubuntu 的 `sh` 是 dash，不支持 `[[ ]]`。巡检脚本用 bash shebang，加上 `set -euo pipefail`，cron 别指望 `.bashrc`。

## 第 5 题：`proxy_pass` 多一个斜杠，接口全 404

### 题目

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;     # 无尾斜杠
}
```

发布后同事改成：

```nginx
    proxy_pass http://127.0.0.1:8080/;    # 多了一个 /
```

之后访问 `http://站点/api/user` 经 Nginx 变成 404。  
直连 `http://127.0.0.1:8080/api/user` 仍是 200。首页静态页 200。

1. 带不带尾斜杠，路径分别怎么变？
2. 用哪些命令证明是路径被改写，而不是后端挂了？
3. 改配置的安全顺序是什么？如何回滚？
4. 为什么「首页 200 + /api 404」不能再一次定论成后端没起来？

### 标准答案

规则（location 带 URI 前缀时）：

```text
proxy_pass 没有 URI（只有 scheme://host:port）
  → 把原始请求 URI 原样转给上游
  /api/user  →  http://127.0.0.1:8080/api/user

proxy_pass 带 URI（注意 / 也是 URI）
  → 用这个 URI 替换掉 location 匹配到的前缀
  location /api/  +  proxy_pass http://127.0.0.1:8080/
  /api/user  →  http://127.0.0.1:8080/ + user  →  /user
```

后端若只认 `/api/user`，改完就会 404。这是 **Nginx 路径拼接**，不是 Spring 挂了。

```bash
# 1. 证明静态页和 80 还在
curl -sI http://127.0.0.1/ | head

# 2. 经 Nginx 失败，直连带 /api 成功
curl -sI http://127.0.0.1/api/user
curl -sI http://127.0.0.1:8080/api/user      # 200
curl -sI http://127.0.0.1:8080/user          # 多半 404，这就是被改写后的路径

# 3. 看 error/access 以及实际配置
tail -n 50 /var/log/nginx/access.log
tail -n 50 /var/log/nginx/error.log
nginx -T | grep -A20 'location /api'
ss -tlnp | grep ':8080'
```

安全变更：

```bash
cp -a /etc/nginx/conf.d /etc/nginx/conf.d.bak.$(date +%F-%H%M)
# 改回不带尾斜杠，或按后端真实 context-path 显式写
# proxy_pass http://127.0.0.1:8080;     # 保留 /api
nginx -t
systemctl reload nginx
curl -sI http://127.0.0.1/api/user
curl -sI http://127.0.0.1:8080/api/user
```

回滚：把备份 conf 拷回，再 `nginx -t && reload`，用同一组 curl 验证。不要 `restart` 抢空间式地中断长连接。

首页 200 + `/api` 404：和第 2 轮「首页 200 /api 502」一样，**只能排除整机/80/静态资源**，排除不了路径改写、`proxy_pass` 斜杠、后端 context-path。直连 8080/api 200 已经把「后端没起来」否掉了。

### 面试可背模板

> `proxy_pass` 没写路径就原样转发；写了 `/` 就会把 location 前缀剥掉。`/api/user` 会变成上游 `/user`。先直连 8080/api 和 8080/user 对照，再 `nginx -T` 看配置。改完备份 → `nginx -t` → reload → curl，失败回备份。

### 详细口述模板（按面试官小问答）

**开口：**  
直连 `/api/user` 200、走 Nginx 404，后端活着。先怀疑 `proxy_pass` 把路径改写了，尤其是多一个 `/`。

**1. 斜杠怎么变**  
不带 URI：`/api/user` → 上游 `/api/user`。  
带 `/`：剥掉 `location /api/`，变成上游 `/user`。

**2. 证明命令**  
`curl` 经 Nginx、直连 `/api/user`、直连 `/user` 三组对照；`nginx -T` 看实际生效配置；`ss` 确认 8080 还在。

**3. 变更闭环**  
备份 conf → 改 → `nginx -t` → `reload` → 再 curl。失败拷回备份再 `nginx -t && reload`。

**4. 为什么不能定论后端挂了**  
首页 200 只说明 80 和静态页在。直连 8080/api 200 已经证明应用在。这是代理路径问题。

**30 秒压缩版：**  
`proxy_pass` 多一个 `/` 会丢掉 `/api` 前缀。三组 curl 对照就能定性。改配置走备份、`nginx -t`、reload、回滚。
