# 第 1 题：Nginx 启动失败

## 题目

线上一台 Linux 服务器执行 `systemctl status nginx` 显示启动失败。

请说明：

1. 排查顺序是什么？
2. 用哪些命令？
3. 如果是配置文件错误，修复前后分别做什么？
4. 如何避免直接改线上配置造成更大影响？

### 追问

```text
nginx -t
nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
```

1. 这条报错是什么意思？
2. 用什么命令确认谁占用了 80 端口？
3. 如果是 Apache/httpd，怎么处理？
4. 为什么处理前不能直接 `kill -9`？

## 你的现场回答（摘要）

- 主答：用 systemd 命令和配置验证命令看 server 配置；再查 Nginx 日志。
- 追问：80 端口被占用；用 `lsof -i :80`；再用 `ps aux | grep httpd/apache` 找 PID，然后 kill，再重启 Nginx。

## 评分

| 项 | 分 |
|---|---|
| 主答方向 | 7.5 / 10 |
| 追问处理 | 7.5 / 10 |

扣分点：命令不够具体；生产环境默认 `kill` 风险大。

## 标准答案

排查顺序：

```text
看失败状态 → 检查配置语法 → 看 systemd/Nginx 日志
→ 查端口占用、权限、SELinux → 备份后修复
→ nginx -t → reload/start → curl 验证
```

关键命令：

```bash
systemctl status nginx --no-pager
nginx -t
journalctl -u nginx -n 50 --no-pager
tail -n 50 /var/log/nginx/error.log

ss -tlnp | grep ':80'
lsof -iTCP:80 -sTCP:LISTEN -nP

# 修复前备份
cp -a /etc/nginx/nginx.conf /etc/nginx/nginx.conf.bak.$(date +%F-%H%M)
# 或备份整个 conf.d
cp -a /etc/nginx/conf.d /etc/nginx/conf.d.bak.$(date +%F-%H%M)

nginx -t
systemctl reload nginx    # 已在跑用 reload；没起来才 start
systemctl status nginx --no-pager
curl -I http://127.0.0.1
```

`Address already in use` 的意思：80 端口已被其他进程占用，Nginx 绑不上。

正确处理 Apache/httpd：

```bash
systemctl status httpd
# Debian/Ubuntu 可能是 apache2
systemctl status apache2

# 确认它不是线上必须服务后，优雅停止，而不是 kill -9
systemctl stop httpd
systemctl disable httpd

ss -tlnp | grep ':80'
nginx -t
systemctl start nginx
curl -I http://127.0.0.1
```

不要默认 `kill -9` 的原因：

- 可能只杀掉一个进程，worker 还在；
- systemd 可能把服务再拉起来；
- 跳过清理，连接和日志可能不完整；
- 没确认这个进程是不是线上业务，可能误停生产服务。

## 面试可背模板

> 先 `systemctl status nginx` 看失败摘要，再 `nginx -t` 查配置语法。配置没问题就看 `journalctl -u nginx` 和 `error.log`。如果是 80 端口占用，用 `ss -tlnp | grep ':80'` 确认进程。若是 httpd 且确认不该运行，用 `systemctl stop` 优雅停止，再 `nginx -t`、启动 Nginx，最后 `curl -I` 验证。改配置前先备份。

# 第 2 题：网站连接超时 · 分层排障

## 题目

用户访问 `www.example.com` 连接超时。服务器 IP `10.0.0.10`，Nginx 监听 80。

从客户端到服务器逐层排查，至少覆盖：

- DNS 是否解析到 10.0.0.10
- 客户端网络、网关、路由
- 服务器网卡和 IP
- 80 端口是否监听
- 防火墙 / 安全组
- Nginx 是否正常
- 本机 curl 是否正常
- 本机通、外网超时，问题范围在哪

### 追问 A

```text
dig 解析正确
ping 10.0.0.10 通
ss 显示 0.0.0.0:80 nginx
本机 curl -I http://127.0.0.1  返回 200
外部用户仍然超时
```

Nginx 还是不是问题？下一步查什么？云主机重点看什么？

### 追问 B

```text
firewalld 未运行
云安全组已放行 80
tcpdump 在服务器上完全抓不到外部访问包
```

请求被挡在哪？如果前面还有 LVS / SLB / CDN，怎么继续定位？

## 你的现场回答（摘要）

- 主答：按 TCP/IP 从下往上，查网卡/`ip a`、网关/`ip r`、ping 网关再 ping 目标、`ss` 看端口、防火墙、再查 DNS/`nslookup`、再用 curl 查 HTTP，最后看服务日志。
- 追问 A：Nginx 大概率正常，下一步查对外通信和防火墙；云主机主要看防火墙。
- 追问 B：防火墙没问题，就是对外网络通信问题。

## 评分

| 项 | 分 |
|---|---|
| 主答 | 7 / 10 |
| 追问 A | 8 / 10 |
| 追问 B | 6.5 / 10 |

扣分点：DNS 放太晚；`ping` 不通不能直接判网络死；命令名称要写准（`ss -tlnp`、`curl`）；追问 B 把“包没到网卡”说成“服务器对外通信”，方向反了。

## 标准答案

推荐顺序：

```text
先确认现象和访问方式
→ DNS（用户访问的是域名）
→ 客户端 IP/网关/路由
→ ping 只能当参考，必须测 TCP 80
→ 服务器网卡/IP
→ ss 看 80 是否监听
→ 云安全组 和 主机防火墙 分开查
→ Nginx 状态 + nginx -t
→ 本机 curl 127.0.0.1 绕过外网
→ 本机 200、外网超时：问题在入口链路，不在 Nginx 本身
```

关键命令：

```bash
# 客户端 / 任意一台能访问公网的机器
dig A www.example.com
dig AAAA www.example.com
ip addr
ip route
ping -c 3 10.0.0.10
nc -zv -w 5 10.0.0.10 80
curl -v --connect-timeout 5 http://10.0.0.10/
curl -v --resolve www.example.com:80:10.0.0.10 http://www.example.com/

# 服务器
ip link show
ip addr show
ss -tlnp | grep ':80'
systemctl status nginx --no-pager
nginx -t
curl -I http://127.0.0.1
firewall-cmd --state
firewall-cmd --list-all
# 或
nft list ruleset
iptables -L -n -v

# 云主机：控制台看安全组入方向 TCP 80、绑定的网卡、网络 ACL

# 判断包有没有到达这台机器
tcpdump -ni any tcp port 80
```

本机 200 + 外部超时，说明 Nginx 大概率正常。要区分：

- **云安全组 / 网络 ACL**：云平台边界防火墙
- **firewalld / nftables / iptables**：主机内部防火墙

`tcpdump` 完全抓不到外部 SYN，说明请求**没到这台服务器网卡**。不是“服务器出站网络”优先，而是入口链路：

```text
客户端 → DNS/CDN → 负载均衡/LVS → 云安全组/ACL → 路由 → 服务器网卡
```

下一步：

1. 再确认客户端解析到的 IP 是不是这台机器（会不会是 VIP / 旧 IP / 错误 AAAA）。
2. 查 LVS / SLB 后端池、健康检查、监听器。
3. 查 CDN / WAF 回源。
4. 入口和后端同时抓包：入口无包看更上游；入口有、后端无，看转发。

## 面试可背模板

> 用户访问的是域名，我先 `dig` 确认是否解析到目标 IP。再查客户端路由，并用 `nc`/`curl` 测 TCP 80，因为 ping 不通不一定等于网络不通。服务器上用 `ss -tlnp` 看监听，本机 `curl 127.0.0.1` 绕过外网。本机 200、外网超时，就重点查云安全组和主机防火墙。如果 `tcpdump` 连 SYN 都没有，问题在服务器之前：DNS、VIP、负载均衡、安全组或上游路由。

# 第 3 题：Nginx 反向代理 502

## 题目

```text
客户端 → Nginx → Spring Boot
location /api/ { proxy_pass http://127.0.0.1:8080; }
访问 /api/user 返回 502 Bad Gateway
```

1. 502 通常表示哪一段出问题？
2. 先执行哪些命令？
3. 如何确认后端进程、8080 监听？
4. 如何绕过 Nginx 直接测后端？
5. 看哪些日志？
6. 后端刚重启还要考虑什么？

### 追问 A

```text
connect() failed (111: Connection refused) while connecting to upstream
upstream: "http://127.0.0.1:8080/api/user"
ss -tlnp | grep ':8080'   无输出
```

### 追问 B

```text
systemctl status myapp → Active: failed (Result: exit-code)
journalctl 出现：
APPLICATION FAILED TO START
Failed to configure a DataSource:
Failed to determine a suitable driver class
```

## 你的现场回答（摘要）

- 主答：502 是网关错误，后端没正常返回；`ss` 看 8080；curl 后端；看 Nginx 日志；有负载均衡再定位具体节点。
- 追问 A：本地 8080 没监听；看 myapp 状态，不正常就启动，再看是否监听。
- 追问 B：未单独完整作答（后续转第 4 题）。

## 评分

| 项 | 分 |
|---|---|
| 主答 | 7.5 / 10 |
| 追问 A | 8 / 10 |

扣分点：502 不等于后端 API 代码一定写错；`ss` 只能证明监听，不能证明接口健康；生产上不要“挂了就 start”，先看为什么退出。`127.0.0.1:8080` 是本机后端，不是负载均衡节点。

## 标准答案

502 的准确含义：

> Nginx 作为反向代理，没有从上游拿到有效 HTTP 响应。

常见原因分类：

| 日志/现象 | 优先怀疑 |
|---|---|
| Connection refused | 没监听、地址/端口错、被拒绝 |
| upstream timed out | 后端慢、依赖卡住、超时过短 |
| prematurely closed connection | 后端崩溃、提前断开 |
| 直接 curl 后端正常，走 Nginx 502 | proxy_pass / upstream / SELinux / 超时配置 |

排查命令：

```bash
tail -n 100 /var/log/nginx/error.log
systemctl status myapp --no-pager
journalctl -u myapp -n 100 --no-pager
ps -ef | grep '[j]ava'
ss -tlnp | grep ':8080'

curl -v --connect-timeout 5 http://127.0.0.1:8080/api/user
curl -v http://127.0.0.1:8080/actuator/health

systemctl cat myapp
df -h
free -h
dmesg -T | grep -i -E 'oom|killed process'
```

修复后验证必须四件事都做：

```bash
systemctl is-active myapp
ss -tlnp | grep ':8080'
curl -v http://127.0.0.1:8080/api/user
curl -v http://127.0.0.1/api/user
tail -n 20 /var/log/nginx/error.log
```

追问 B：这是 **Java 应用启动/配置/依赖问题**，不是 Nginx 问题。  
`Failed to determine a suitable driver class` 通常是：

- 当前 Spring Profile 不对；
- 数据源 URL/账号没配上；
- JDBC 驱动没打进包；
- 环境变量或挂载的配置文件没生效；
- systemd `Environment=` / `EnvironmentFile=` 写错。

处理：先改对配置和依赖，确认数据库本身能连，再启动应用，最后再测 Nginx。

## 面试可背模板

> 502 说明 Nginx 没拿到上游有效响应。先看 error.log 区分 refused / timeout / 提前断开。再查后端进程、`ss` 看 8080，并直接 `curl 127.0.0.1:8080`。后端自己就失败，就查 systemd 日志和应用依赖，不要先动 Nginx。后端直接访问正常、走代理才 502，再查 proxy_pass 和超时。验证不能只看 status，必须进程、端口、直连 HTTP、经 Nginx HTTP 都过。

# 第 4 题：Nginx 高并发优化（标准讲义）

## 题目

静态资源 + 反向代理。访问量上来后：

- CPU 不高
- `worker_connections` 接近上限
- 日志偶发 `too many open files`

请说明：

1. `worker_processes` 和 `worker_connections` 的关系，最大并发怎么算？
2. `too many open files` 的根因和三层限制？
3. 为什么调大连接数必须同步改 `worker_rlimit_nofile` 和 `ulimit`？
4. 静态资源和反向代理分别还能优化什么？
5. 4 核机器给一套初始参数。
6. 怎么验证？为什么不能凭感觉调大？

## 你的处理

这题你明确说不会，按训练规则改为讲解，不评分。

## 标准答案

### 1. 并发怎么算

```text
理论最大连接数 ≈ worker_processes × worker_connections
例：4 × 10240 = 40960
```

注意：

- 反向代理时，客户端连接 + 到后端连接，一个请求可能占 **2 个 fd**；
- 还受内存和系统 fd 上限限制，理论值到不了。

### 2. too many open files

Linux 里连接也是文件。连接数涨 → fd 用尽 → 报 `too many open files`。

三层限制，取最小值：

| 层级 | 位置 | 常见默认 |
|---|---|---|
| Nginx 进程 | `worker_rlimit_nofile` | 常未设置 |
| 用户/进程 | `ulimit -n`、limits.conf、systemd `LimitNOFILE` | 1024 |
| 系统全局 | `fs.file-max` | 内核上限 |

### 3. 为什么必须联动

```text
worker_connections = 20000
→ 每个 worker 可能需要 20000 甚至 40000 个 fd
→ worker_rlimit_nofile ≥ worker_connections × 2
→ ulimit / systemd LimitNOFILE 也要 ≥ 这个值
→ 少一层就会继续报 too many open files
```

```bash
# 临时
ulimit -n 65535

# 永久：/etc/security/limits.conf
* soft nofile 65535
* hard nofile 65535

# systemd 托管的 Nginx 还要：
# /etc/systemd/system/nginx.service.d/override.conf
[Service]
LimitNOFILE=65535

systemctl daemon-reload
systemctl restart nginx

# 验证真实生效值
cat /proc/$(pgrep -n -f 'nginx: worker')/limits | grep -i nofile
```

### 4. 除了连接数还能优化什么

静态资源：

```nginx
sendfile on;
tcp_nopush on;
open_file_cache max=1000 inactive=60s;
gzip on;
expires 7d;
```

反向代理：

```nginx
proxy_http_version 1.1;
proxy_set_header Connection "";
upstream backend {
    server 127.0.0.1:8080;
    keepalive 32;
}
proxy_buffering on;
proxy_connect_timeout 5s;
```

网络 / 进程：

```nginx
worker_cpu_affinity 0001 0010 0100 1000;
events { use epoll; }
```

### 5. 4 核初始组合

```nginx
worker_processes 4;
worker_cpu_affinity 0001 0010 0100 1000;
worker_rlimit_nofile 65535;

events {
    use epoll;
    worker_connections 10240;
}
```

系统：`nofile 65535`。

### 6. 验证闭环

```text
基线压测 → 改参数 → 再压测对比 → 看错误率和延迟 → 异常回滚
```

```bash
wrk -t4 -c1000 -d60s http://example.com/
# 记录 QPS、延迟、错误率、内存、fd

ss -s
tail -f /var/log/nginx/error.log
```

改配置：备份 → `nginx -t` → `reload` → 观察 5–10 分钟。

`reload` 平滑替换 worker，连接不断；`restart` 会中断。

### 常见追问速记

- `worker_processes auto`：等于 CPU 核数；IO 密集可略多。
- gzip 耗 CPU，图片视频不要压。
- keepalive 省的是反复握手。

## 面试可背模板

> 最大并发约等于 worker 数乘以每进程连接数。每个连接占 fd，所以要同时放开 Nginx 的 `worker_rlimit_nofile`、系统 `ulimit` 和 `fs.file-max`。反代场景 fd 按连接数两倍留余量。静态站开 sendfile/缓存/gzip，反代开 upstream keepalive 和合理超时。4 核我通常用 4 个 worker、10240 连接、65535 fd。所有调整先压测建基线，用数据对比，配置先备份再 `nginx -t` 再 reload。

# 第 5 题：Spring Boot JAR 发布与回滚

## 题目

把新的 Spring Boot JAR 发到生产。systemd 管理 `myapp`。

要求：少中断、失败能回滚、发布前后都能验证；**不能只看 `systemctl status` 就算成功**。

设计完整流程：发布前检查、包和配置、备份版本、停/换/启、进程端口、日志、HTTP 健康检查、失败回滚、发布记录。

## 标准答案（本题你尚未现场作答，先按这个背）

### 1. 发布前检查

```bash
# 当前服务是否健康，不健康先别发
systemctl is-active myapp
ss -tlnp | grep ':8080'
curl -fsS --connect-timeout 3 http://127.0.0.1:8080/actuator/health
df -h
free -h
java -version

# 看当前进程真正跑的是哪个 jar
systemctl cat myapp
ps -ef | grep '[j]ava'
```

确认：磁盘够、Java 版本匹配、健康检查现在是通的、有回滚包可回。

### 2. 版本目录，不要覆盖正在跑的文件

推荐结构：

```text
/opt/myapp/
  current -> releases/20260812-1530
  releases/
    20260812-1200/app.jar
    20260812-1530/app.jar
  conf/
    application-prod.yml
  logs/
```

```bash
STAMP=$(date +%Y%m%d-%H%M)
NEW=/opt/myapp/releases/$STAMP
mkdir -p "$NEW"
cp -a /tmp/app-new.jar "$NEW/app.jar"
# 配置也纳入版本，避免只换 jar 忘了配
cp -a /opt/myapp/conf "$NEW/conf"

# 记录旧版本
OLD=$(readlink -f /opt/myapp/current)
echo "$OLD" > /tmp/myapp.prev
```

### 3. 停服务 → 切版本 → 启动

```bash
systemctl stop myapp
# 确认进程和端口都下来了
ss -tlnp | grep ':8080' || echo '8080 free'
ln -sfn "$NEW" /opt/myapp/current
systemctl start myapp
```

单机 unavoidably 会有短暂中断。能接受就这样；要求更少中断要上双实例/滚动，那是下一阶段。

systemd 示例（`ExecStart` 指向 current，不要写死旧路径）：

```ini
[Service]
WorkingDirectory=/opt/myapp/current
ExecStart=/usr/bin/java -jar /opt/myapp/current/app.jar --spring.profiles.active=prod
Restart=on-failure
```

### 4. 验证：四件事，缺一不可

```bash
systemctl is-active myapp
journalctl -u myapp -n 80 --no-pager
ss -tlnp | grep ':8080'
curl -fsS --connect-timeout 5 http://127.0.0.1:8080/actuator/health
curl -fsS --connect-timeout 5 http://127.0.0.1/api/user
```

`systemctl is-active` 只能说明进程被 systemd 拉起来了，**不能说明业务可用**。  
必须看到：端口在听、健康检查 200、关键接口有正确响应、error 日志没有持续报错。

建议观察 1–3 分钟，看有没有启动后立刻退出或 OOM。

### 5. 失败立刻回滚

任何一步失败（启动失败、没有 8080、health 失败、核心接口 5xx）：

```bash
systemctl stop myapp
ln -sfn "$(cat /tmp/myapp.prev)" /opt/myapp/current
systemctl start myapp

systemctl is-active myapp
ss -tlnp | grep ':8080'
curl -fsS http://127.0.0.1:8080/actuator/health
curl -fsS http://127.0.0.1/api/user
```

回滚后也要走同一套验证，不能“切回去就算好了”。

### 6. 发布记录

至少记下：

- 时间、操作人
- 旧版本路径、新版本路径、git/构建号
- 发布前健康状态
- 发布后验证命令和结果
- 是否回滚、原因
- 遗留风险（慢查询、连接数、错误率）

## 面试可背模板

> 发布前先确认当前健康、磁盘和 Java 版本，并把旧目录记下来。新 jar 放到带时间戳的 releases 目录，不要覆盖正在运行的文件。停服务、切换 current 软链接、再启动。验证必须包括 systemd 状态、8080 监听、actuator health、经 Nginx 的业务接口。失败就切回旧链接并重新验证。最后记录版本和验证结果。只看 systemctl status 不算发布成功。

## 常见追问

1. **为什么不要直接覆盖正在跑的 jar？**  
   进程可能还映射着旧文件；覆盖后回滚没得回，也可能写到一半就停服务。
2. **stop 之后 start 前为什么要确认端口已释放？**  
   旧进程没退干净会 `Address already in use`，新进程起不来。
3. **健康检查 200 但业务接口 500 算成功吗？**  
   不算。health 只能说明进程活着，核心交易/查询接口也要抽查。
4. **能不能先启动新端口再切流量？**  
   可以，那是蓝绿/双实例。单机单端口做不到零中断，面试里主动说出来加分。
