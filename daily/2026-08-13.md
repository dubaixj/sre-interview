## 第 1 题：磁盘看起来还有空间，但写不了文件

### 题目

线上 Nginx 错误日志突然不再更新，应用也报无法写文件。`df -h` 显示根分区还剩 40% 空间。

1. 除了「磁盘满」，还有哪些常见原因会导致无法创建/写入文件？
2. 按什么顺序排查？写出命令。
3. 如果是 inode 耗尽，怎么确认、怎么处理？注意什么？
4. 如果日志把某个目录写爆、但 `df -h` 根分区看起来还够，可能漏查了什么？

### 标准答案

常见原因：inode 耗尽、只读挂载、权限/属主、目录不可写、SELinux/AppArmor、磁盘配额、文件被删但仍被进程占用（空间未释放）、写到了别的挂载点。

```bash
df -h
df -i
mount | grep ' / '
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS /
ls -ld /var/log /var/log/nginx
namei -l /var/log/nginx/error.log
lsattr /var/log/nginx
getenforce
quota -vs
lsof +L1 | head
df -hT
```

inode 耗尽：`df -i /var/log/nginx` 的 IUse% 到 100%。定位：`du --inodes -x -d 1 /var | sort -n`。处理：确认是缓存/session/临时文件再删，不要盲删业务数据。有用的小文件打 tar 后必须删原文件，inode 才会回来。不要一上来加硬盘。清完再 `df -i` 和 `touch` 验证。

`df -h` 根分区够、但仍写爆：可能 `/var`、`/home`、日志盘是独立分区，或容器/应用写到了数据盘。要对具体日志路径做 `df -h /var/log/nginx`。

### 面试可背模板

> 空间看起来够，还要查 inode、挂载是否只读、权限、配额，以及日志目录所在分区。`df -h` 和 `df -i` 一起看，再对具体路径做 `df -h /path`。inode 满就清大量小文件，删前确认目录。

### 详细口述模板（按面试官 4 问对答）

**开口：**  
`df -h` 根分区剩 40%，只能说明根分区块空间没满，不能说明「一定能写成文件」。写文件还要：这块盘有 inode、文件系统可写、目录有权限、没被配额/SELinux 卡住，而且日志可能不在根分区上。

**1. 除了磁盘满，还有哪些原因**  
inode 耗尽；分区只读；权限/属主不对；SELinux/AppArmor；磁盘配额；文件已删但进程还占着 fd（空间没释放）；实际写到了另一个挂载点。

**2. 排查顺序（对着日志路径查，不要只查 /）**

```bash
df -h /var/log/nginx
df -i /var/log/nginx
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS /var/log/nginx
ls -ld /var/log /var/log/nginx
namei -l /var/log/nginx/error.log
lsof +L1 | head
```

先看空间和 inode，再看是否 `ro`，再看权限，再看已删未释放。

**3. inode 耗尽**  
确认：`df -i /var/log/nginx` 的 IUse% 到 100%。  
定位：`du --inodes -x -d 1 /var | sort -n`，找文件个数特别多的目录。  
处理：确认是缓存/session/临时文件再删；不要盲删业务数据。有用的小文件打 tar 之后必须删原文件，inode 才会回来。  
不要一上来加硬盘：新盘是新文件系统，救不了当前这个文件系统的 inode。  
清完验证：再跑 `df -i`，`touch` 试写，看 Nginx 日志是否重新滚动。

**4. 根分区够、日志却写爆**  
漏查了日志路径所在分区。`/var`、`/home`、日志盘经常独立挂载。必须 `df -h /var/log/nginx`，不能只看根分区。

### 现场记录

- 作答：先 `df -h` 确认根分区剩 40%；首选 inode 耗尽 → `df -i` → 到 inode 占用高的目录用 `find` 找小文件 → 无用则删、有用则打包释放 inode；再不行就加硬盘。
- 评分：主答 6 / 10（inode 方向对，但当成唯一原因；命令不完整；漏分区/权限/只读/配额/已删未释放）
- 扣分点：`find` 没写出具体命令；把小文件说成「占内存小」；inode 满默认加硬盘不对；没对日志路径做 `df -h /var/log/nginx`；没写清理后验证
- 追问：答「目前只能想到 inode，其他没思路」→ 改讲解，不再硬评分
- 讲解要点：写不进去 ≠ 只有 inode；必须对日志路径做 `df -h /var/log/nginx`；只读挂载 / 权限 / 配额 / 已删未释放 / 独立分区

## 第 2 题：ping 通，但网站打不开

### 题目

```text
ping 10.0.0.10          通
curl http://10.0.0.10   Connection refused
```

1. `Connection refused` 和 `Connection timed out` 分别说明什么？
2. 此时还要不要先查云安全组？为什么？
3. 下一步命令是什么？每条证明什么？
4. 若 Nginx 只听 `127.0.0.1:80` 而不是 `0.0.0.0:80`，说明什么？

### 标准答案

- **refused**：SYN 到达主机，但该端口没有进程在听，或被明确拒绝。安全组通常不是首选（安全组丢包更像 timeout）。
- **timeout**：包被丢弃或中途不可达，常见于安全组、防火墙 DROP、路由、服务不在那台机器。

```bash
ss -tlnp | grep ':80'
curl -v --connect-timeout 5 http://127.0.0.1/
nginx -t
systemctl status nginx --no-pager
grep -n listen /etc/nginx/nginx.conf /etc/nginx/conf.d/*.conf
```

`listen 127.0.0.1:80` 只对本机开放。外网会 refused 或连不上。改为 `listen 80;` 或 `0.0.0.0:80`，`nginx -t` 后 reload，再用本机和外网 curl 验证。

### 面试可背模板

> ping 通只说明 ICMP 通。refused 说明包到了主机但端口没人听或只听本地。先 `ss -tlnp` 看监听地址，再本机 curl。不要先去改安全组。

### 详细口述模板（按面试官 4 问对答）

**开口：**  
`ping` 通只证明 ICMP 通，不证明 80 端口通，也不证明 HTTP 正常。本题关键报错是 `Connection refused`，不是 timeout，分层要从这个词开始。

**1. refused 和 timeout 分别说明什么**  
- `Connection refused`：SYN 已经到这台机器，内核回了 RST。常见原因是该端口没有进程在听，只听了 `127.0.0.1`，或主机防火墙是 REJECT。  
- `Connection timed out`：包中途被丢或根本没到。常见原因是云安全组、主机防火墙 DROP、路由不对、IP 指错机器。

**2. 此时还要不要先查云安全组**  
不要。安全组丢包通常是 timeout，不是 refused。refused 说明包已经进主机了，先查本机监听。timeout 才优先拆两层：云安全组和主机防火墙。

**3. 下一步命令，每条证明什么**

```bash
ss -tlnp | grep ':80'          # 80 有没有人听，听在 0.0.0.0 还是 127.0.0.1
curl -v --connect-timeout 5 http://127.0.0.1/   # 本机 HTTP 通不通
nginx -t                       # 配置能不能过
systemctl status nginx --no-pager
grep -n listen /etc/nginx/nginx.conf /etc/nginx/conf.d/*.conf
```

没有监听：查 Nginx 是否起来、是否绑错端口。  
只听 `127.0.0.1`：改 listen。  
本机 curl 通、外网 refused：就是绑本地的问题。

**4. 只听 127.0.0.1:80**  
只对本机开放，外网连 80 会 refused。改成 `listen 80;` 或 `listen 0.0.0.0:80;`。  
处理闭环：备份配置 → `nginx -t` → `systemctl reload nginx` → 本机 curl + 外网 curl。

### 现场记录

- 作答：ping 通但网站打不开，先当服务器问题；先查安全组是否放行；再用 `ss -lntp` 看端口是否监听；若是 `127.0.0.1` 则改 Nginx `listen 0.0.0.0:80` 或 `listen 80`。
- 评分：主答 5.5 / 10；追问 8 / 10
- 扣分点：主答把安全组放第一；没写本机 `curl`、`nginx -t`、reload 后内外网验证
- 追问：refused = 包到了主机但端口没人听；timeout = 包没到主机，查防火墙。口径对，安全组/主机防火墙还没拆开。

## 第 3 题：发布后首页正常，接口全 502

### 题目

Nginx 静态 Vue + `proxy_pass /api/` → `127.0.0.1:8080`。发布后首页 200，`/api/*` 全 502。

1. 这个现象能排除哪些问题？
2. 如何区分 Nginx 配置、后端没起来、路径变了？
3. 写出关键命令。
4. 直连 8080 也失败，和只经 Nginx 失败，处理有何不同？

### 标准答案

能排除：整机宕机、DNS 全挂、80 完全没监听、静态资源目录没了。

```bash
curl -I http://127.0.0.1/
curl -v http://127.0.0.1/api/user
tail -n 80 /var/log/nginx/error.log
ss -tlnp | grep ':8080'
curl -v http://127.0.0.1:8080/api/user
curl -v http://127.0.0.1:8080/actuator/health
systemctl status myapp --no-pager
journalctl -u myapp -n 80 --no-pager
nginx -T | grep -A20 'location /api'
```

直连 8080 失败：查应用进程、配置、依赖。直连成功、走 Nginx 502：查 `proxy_pass` 斜杠、upstream、超时、SELinux。

### 面试可背模板

> 首页 200 说明 Nginx 和静态资源大致正常，问题在 /api 代理或后端。先看 error.log 分类，再直连 8080。两边都失败查应用；只有代理失败查 Nginx location。

### 详细口述模板（按面试官 4 问对答）

**开口：**  
首页 200、`/api` 全 502，只能说明静态页和 80 端口大致正常，问题在 `/api` 这一跳。不能直接定论后端没起来。

**1. 这个现象能排除什么**  
能排除：整机宕机、DNS 全挂、80 没人听、静态资源目录没了、Nginx 完全没起来。  
排除不了：后端没起来、`proxy_pass` 配错、路径变了、后端自己 502。

**2. 怎么区分三件事**  
- 后端没起来：`ss` 没有 `:8080`，直连 8080 失败。  
- Nginx 配错：直连 8080 成功，走 `/api` 仍 502。重点看 `proxy_pass` 斜杠。  
- 路径变了：直连 `8080/api/user` 404 或路径不对，但进程和端口是好的。

**3. 关键命令**

```bash
curl -I http://127.0.0.1/
curl -v http://127.0.0.1/api/user
tail -n 80 /var/log/nginx/error.log
ss -tlnp | grep ':8080'
curl -v http://127.0.0.1:8080/api/user
systemctl status myapp --no-pager
journalctl -u myapp -n 80 --no-pager
nginx -T | grep -A20 'location /api'
```

error.log 先分类：`connect() failed` / `timed out` / `prematurely closed`。

**4. 两种失败处理不同**  
直连 8080 失败：查应用进程、配置、依赖，不要先改 Nginx。  
直连成功、只走 Nginx 502：查 `proxy_pass` 斜杠、upstream、超时。改完 `nginx -t` → reload → 再 curl `/api`。

### 现场记录

- 作答：首页 200、/api 502 直接判后端没起来；`ss -lntp | grep :8080` 没起来就是后端问题；直连 8080 失败查后端，直连成功、走 Nginx 502 查 Nginx 配置和日志。
- 评分：主答 6 / 10（两条分支说对了，但把现象直接当成后端没启动；命令几乎只有 ss）
- 扣分点：没说能排除什么；没写 curl / error.log / journalctl；没提 proxy_pass 斜杠和路径变化
- 追问：答「不会」→ 改讲解，不再硬评分

## 第 4 题：重启后服务没起来

### 题目

昨晚发布正常。机器重启后 `nginx` 和 `myapp` 都是 `inactive`。

1. `start` 成功和开机自启是不是一回事？
2. 如何确认有没有 enable？
3. 如何安全打开开机自启并验证？
4. 已 enable 但开机仍失败，查什么？

### 标准答案

不是一回事。`start` 只影响当前运行；`enable` 写开机链接。

```bash
systemctl is-enabled nginx myapp
systemctl status nginx myapp --no-pager
ls -l /etc/systemd/system/multi-user.target.wants/ | grep -E 'nginx|myapp'
systemctl enable nginx myapp
systemctl is-enabled nginx myapp
# 不要在生产随便 reboot 做实验；可看
systemd-analyze blame
journalctl -u nginx -b
journalctl -u myapp -b
```

开机失败常见：依赖的网络/磁盘还没好、`After=` 写错、配置在重启后语法错、工作目录或 jar 路径是相对路径。

### 面试可背模板

> start 不等于 enable。用 `systemctl is-enabled` 确认，需要的服务 `enable`。开机仍失败看本轮启动日志 `journalctl -u xxx -b`，不要只看当前 inactive。

### 详细口述模板（按面试官 4 问对答）

**开口：**  
`systemctl start` 成功只说明这一次起来了，不说明重启后还会起来。开机自启是另一件事，要看 `enable` 有没有写上。

**1. start 和开机自启是不是一回事**  
不是。`start` / `restart` 只影响当前这次运行。`enable` 才在开机目标里加软链。生产上常见坑：发布当晚 `start` 正常，第二天重启机器服务全是 `inactive`。

**2. 怎么确认有没有 enable**

```bash
systemctl is-enabled nginx myapp
systemctl status nginx myapp --no-pager
ls -l /etc/systemd/system/multi-user.target.wants/ | grep -E 'nginx|myapp'
```

要看 `is-enabled` 的输出：`enabled` / `disabled` / `static`。`status` 里那行 `enabled` 只是摘要，不够精确。软链在 `multi-user.target.wants/` 下，才是 enable 的本质。

**3. 怎么安全打开开机自启并验证**

```bash
systemctl enable nginx myapp
systemctl is-enabled nginx myapp
# 需要立刻跑起来再用：
systemctl enable --now nginx myapp
systemctl is-active nginx myapp
```

生产不要拿 `reboot` 做实验，业务会中断。验证看 `is-enabled` 变成 `enabled`，软链在，当前 `is-active` 为 `active`。

**4. 已经 enable，开机却仍失败**  
查本轮开机日志，不要只看现在是 inactive：

```bash
journalctl -u nginx -b --no-pager
journalctl -u myapp -b --no-pager
systemctl cat myapp
systemd-analyze blame
```

`-b` 表示这一轮开机。常见原因：网络/磁盘还没好、`After=` 写错、配置重启后语法错、jar/工作目录写成了相对路径。修好后再 `start`，用进程、端口、HTTP 健康检查验证，不要只看 `systemctl status`。

### 现场记录

- 作答：start 和开机自启不是一回事；start 只启动当次，开机要 `enable`；`enable --now` 可启动并设自启；enable 本质是加软链；已 enable 仍没起来则查配置和软链是否指向正确。确认 enable 用了 `systemctl status`。
- 评分：主答 7 / 10；追问 7.5 / 10
- 扣分点：确认自启用 `status` 不够精确；本轮日志会 `journalctl -u`，漏了 `-b`
- 追问：会用 `journalctl -u myapp`；生产不能 reboot，理由是业务中断。漏了 `-b` 表示「本轮开机」。

## 第 5 题：时间不准引发的「假网络」故障

### 题目

部分用户 HTTPS 报证书错误，个别登录失败。系统时间慢 20 分钟，`System clock synchronized: no`。

1. 时间不准为什么会影响 HTTPS / 登录 / 日志？
2. 如何确认 chrony 是否在同步？
3. 生产上能直接改时间吗？
4. 修好后如何验证？

### 标准答案

证书有 NotBefore/NotAfter；时间偏差大会判证书无效。登录 token/Kerberos 也看时间。日志时间错了会让排障对不上变更窗口。

```bash
date
timedatectl
systemctl status chronyd
chronyc tracking
chronyc sources -v
```

生产不要随便 `date -s` 大幅回调，可能导致数据库、证书、定时任务异常。应修 NTP/chrony，让它逐步校正；必须立即纠正时先评估影响并通知相关方。

验证：`timedatectl` 显示已同步；浏览器/curl HTTPS 不再报证书时间错误；抽查登录；看新日志时间是否正确。

### 面试可背模板

> HTTPS 和登录都依赖正确时间。先 `timedatectl` 和 `chronyc tracking`。优先修时间同步，不要生产上直接拨时钟。修好后验证 HTTPS、登录和日志时间。

### 详细口述模板（按面试官 4 问对答）

**开口：**  
这不是网络挂了，是时间不准引起的假网络故障。证书、登录票据、日志都认墙上的钟。

**1. 为什么影响 HTTPS / 登录 / 日志**  
- HTTPS：证书有 NotBefore / NotAfter。时间慢 20 分钟，新证书可能被判「还没生效」；时间快了会被判过期。  
- 登录：token / cookie / Kerberos / 验证码都校验时间。  
- 日志：时间错了，对不上变更窗口和其他机器。

**2. 怎么确认 chrony 在不在同步**

```bash
date
timedatectl
systemctl status chronyd --no-pager
chronyc tracking
chronyc sources -v
```

`System clock synchronized: no` 就是没同步上。`chronyc tracking` 看偏移，`sources -v` 看上游源通不通。

**3. 生产能不能 date -s**  
不能随便大幅拨时钟。数据库、证书、定时任务、监控会被跳变打乱。应该修 chrony，让它逐步校正。必须立刻纠正时，先评估影响并通知相关方。

**4. 修好后验证**  
`timedatectl` 显示已同步；HTTPS 不再报证书时间错误；抽查登录；新日志时间正确。

### 现场记录

- 作答：表示这题不熟
- 评分：改讲解，不打分
- 追问：无
